Features

Three ways a support bot fails, and how each one gets caught.

01 · Groundedness

Grounded in the manual, or flagged

Each sentence of an answer is matched against the manual text the bot retrieved. Every number and error code must appear in that source, and in Claude mode a separate Claude call judges the whole answer. A wrong temperature fails even when the wording looks right.

  • Semantic match per sentence, threshold 0.75
  • Fact check on every number and code
  • LLM-as-judge with a strict rubric

02 · Safety

Attacked on purpose, before anyone else tries

Fifteen attack prompts (direct and hidden injections, role-play jailbreaks, base64 tricks, system-prompt extraction) plus seven attempts to pull customer data. Four harmless control questions make sure the guardrails don't turn real customers away.

  • On the way in: injection rules, base64 decoded
  • Before the model: poisoned and PII-dense chunks dropped
  • On the way out: leak canary, link allowlist, redaction

03 · Reports

A report for every prompt or model change

Every run stores the model, prompt version and retrieval settings next to its scores, compares itself with a saved baseline and lists each case that newly fails or passes. An unexpected failure exits with code 1, so CI can stop the change.

  • 11 metrics, from groundedness to p95 latency
  • Baseline diff of settings, scores and cases
  • Known issues tracked as xfail, never deleted

How it works

From manuals to a pass/fail verdict in three steps.

Everything runs on your machine. The same commands work in a CI job.

  1. 1

    Step 1: Index your manuals

    Drop a manual onto the chat page (PDF, Word, slides, spreadsheets, web pages, e-books, even scans and photos), or put it in data/manuals. It is cleaned, split into 700-character chunks that keep their headings, and embedded locally.

    uvicorn app.main:app
  2. 2

    Step 2: Run the suites

    pytest starts the API, sends 51 test prompts over HTTP and scores every reply for groundedness, attacks and leaks. Offline, the whole run takes about 19 seconds.

    pytest
  3. 3

    Step 3: Compare and gate

    Save a baseline, change a prompt or model, and run again. The report shows what moved; any unexpected failure exits with code 1.

    python -m evaluation.run_eval --save-baseline

FAQ

Questions before you run it.

Everything else is in the build guide, with one chapter for each step of the build.

Open the build guide (PDF)
Do I need an API key to try it?

No. Without a key, an offline extractive model answers by quoting the manuals, and every report, guardrail and test runs locally for free, except two calibration checks that need the Claude judge. Add ANTHROPIC_API_KEY to .env when you want Claude to write and judge answers.

What counts as a hallucination?

Any claim the retrieved manual text doesn't support: a changed number or error code, an invented feature, or advice that contradicts the source. An answer is flagged when its groundedness score drops below 0.70. Offline checks catch changed numbers and codes and unsupported sentences; contradictions such as a negated instruction need the Claude judge.

How do I switch to Claude?

Copy .env.example to .env, set ANTHROPIC_API_KEY and restart the API. /health then reports the Claude provider and the next run turns on the LLM judge. Save a new baseline so later runs compare Claude with Claude.

Can I test my own manuals and questions?

Yes. Drop your manual onto the chat page, in almost any format: PDF, Word, slides, a web page, or a scan or photo of the pages, read with text recognition. Answers then come only from that manual, with the page and section they came from. To add test questions, put one JSON line per question in golden_qa.jsonl; each line becomes its own pytest test and its own row in the report.

How are prompt-injection attacks stopped?

Four layers: pattern rules on the question (including decoded base64), a filter that drops retrieved chunks containing instructions or customer records, a hardened system prompt with a leak canary, and output checks for unknown links and personal data.

Is any real customer data involved?

No. The manuals and the customer records planted to test leaks are invented: made-up names, phone numbers and addresses, and .example email domains. They are planted on purpose so the PII tests have something to catch.
